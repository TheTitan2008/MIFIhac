# Prompt Radar label guide

Версия: `label-guide-v2`  
Статус: recovery candidate, подлежит freeze до sealed v2  
Единица разметки: одна текущая пользовательская цель

## 1. Назначение

Этот документ задаёт правила разметки, которые применяются одинаково к
development, external opaque challenge и будущим реальным данным. Правила не
выводятся из раскрытого sealed v1 и не могут меняться после recovery freeze до
получения результата независимого sealed v2.

Для OpenAI-compatible payload размечается только `current_user_goal`:

- последний фактический user query;
- не system/developer instruction;
- не предыдущий user turn;
- не assistant response;
- не tool result;
- не RAG source или другой retrieval context;
- не task wrapper вокруг `<user_query>`.

Контекст может подтверждать систему, объект или сложность, но не имеет права
заменить intent текущей цели.

## 2. Общие правила multi-label

1. Label ставится только при построчном evidence в текущей цели.
2. Несколько labels на одной оси допустимы, если цель явно требует несколько
   разных действий, систем или объектов.
3. Общая тема контекста не является evidence для intent.
4. Нельзя наследовать все labels исходной темы каждой её перефразировке.
   Каждая строка размечается отдельно.
5. Порядок labels не имеет значения.
6. Отсутствующий label и `Other` - разные состояния:
   - пустой список означает abstention/недостаток evidence;
   - `Other` означает явную систему вне текущего словаря.
7. Если две интерпретации одинаково правдоподобны и текст не разрешает спор,
   ось abstains. Нельзя выбирать label ради coverage.
8. Для любого gold label annotator сохраняет короткий evidence span из
   `current_user_goal`. Evidence из RAG/history недопустим.

## 3. Ось `system`

Система, с которой пользователь просит выполнить действие.

| Label | Определение и положительное evidence |
|---|---|
| `Email` | Почта, письмо, входящие, переписка, ответ на письмо. |
| `CRM` | CRM, карточка клиента/сделки, продажи или тендеры именно в CRM. |
| `Jira` | Явное Jira или однозначная Jira-задача. |
| `ISUP` | Явное ИСУП. |
| `Project` | Явная доска/система Project. Слово «проект» само по себе недостаточно. |
| `Calendar` | Календарь, свободный слот, создание/поиск встречи, переговорная. |
| `Confluence` | Явное Confluence. |
| `Excel` | Excel/XLSX как источник или требуемый результат. |
| `CoolFeedback` | Явное CoolFeedback. |
| `OpenWeb` | Открытые источники, внешний web-поиск или корпоративный блог. |
| `Other` | Система явно указана, но отсутствует в taxonomy. |

Multi-label ставится для межсистемной цели, например
`«создай задачу Project из письма» -> [Email, Project]`.

## 4. Ось `intent`

Действие, которое должно быть выполнено сейчас.

| Label | Определение |
|---|---|
| `search` | Найти, показать, получить или собрать уже существующую информацию. |
| `summarize` | Сжать, обобщить, структурировать или подготовить обзор содержания. |
| `create` | Создать новый артефакт: письмо, задачу, встречу, запись, отчёт. |
| `update` | Изменить существующий артефакт, поле, статус или содержимое. |
| `reply` | Подготовить/отправить ответ адресату или отзыв. |
| `export` | Выгрузить существующие данные в файл/формат. |
| `monitor` | Периодически проверять состояние или условие. |
| `notify` | Уведомить, напомнить или подсветить событие. |
| `schedule` | Найти совместимое время/место и запланировать встречу. |
| `explain` | Объяснить явление, ошибку или причину. |

### 4.1. `create` против `update`

- `create` ставится, если появляется новый объект.
- `update` ставится, если меняется уже существующий объект.
- Оба labels ставятся только когда текущая цель явно содержит оба действия:
  `«добавь новый тикет и обнови статус существующего»`.
- `«актуализируй тикеты»` - `update`, не `create`.
- `«создай актуальный отчёт»` - `create`; прилагательное «актуальный» не
  является update evidence.
- `«сформируй отчёт из данных»` - `create` и, при явной агрегации содержания,
  возможно `summarize`.
- Нельзя назначать `update` всем перефразировкам темы только потому, что update
  встречался в одной source row.

### 4.2. Составные intents

`«найди данные в CRM и выгрузи в Excel» -> [search, export]`.
Если второе действие является лишь технической деталью первого и не требует
отдельного результата, annotator фиксирует основной intent и спор в журнале.

## 5. Ось `object`

Бизнес-объект действия.

| Label | Определение |
|---|---|
| `email` | Письмо, почта, переписка. |
| `client` | Клиент, компания-клиент, контакт клиента. |
| `deal` | Сделка или продажа. |
| `tender` | Тендер. |
| `task` | Задача, тикет, поручение. |
| `project` | Проект как бизнес-объект, не приложение Project. |
| `meeting` | Встреча, слот встречи, материалы встречи. |
| `room` | Переговорная/комната. |
| `document` | Документ, регламент, страница, source file. |
| `employee_note` | Наблюдение, заметка или feedback о сотруднике. |
| `report` | Отчёт, сводка или аналитическая выгрузка как результат. |

Все явно требуемые объекты сохраняются; искусственного ограничения «не более
двух» нет.

## 6. Ось `automation_mode`

| Label | Определение |
|---|---|
| `one_shot` | Однократное выполнение без явного расписания. |
| `recurring` | Повтор по расписанию/периодичности. |
| `monitoring` | Непрерывная или периодическая проверка условия. |
| `notification` | Срабатывание уведомления/напоминания. |

При явно составном workflow допустимы несколько labels, например
`monitoring + notification`. Если периодичность описывает лишь частоту отчёта,
используется `recurring`.

## 7. Ось `business_domain`

| Label | Определение |
|---|---|
| `sales` | Клиенты, сделки, продажи, тендеры. |
| `projects` | Проекты, project/task management, delivery. |
| `HR` | Сотрудники, руководительская обратная связь, HR-процессы. |
| `knowledge` | Поиск и организация корпоративных знаний. |
| `productivity` | Личная/командная продуктивность, календарь, почта общего назначения. |

Основной domain выбирается по бизнес-результату цели. Если цель действительно
пересекает два равноправных домена, допустим multi-label; RAG-тематика не
создаёт domain label.

## 8. Abstention и quarantine

Ось abstains, если:

- нет прямого evidence;
- текст обрывается или неоднозначен;
- доступен только RAG/history, но текущая цель отсутствует;
- уверенность ниже frozen threshold.

Весь payload quarantined, если:

- `messages` отсутствует или не является непустым списком;
- нет user message;
- role/content имеет неизвестную структуру;
- найдено несколько различных `<user_query>`;
- current user goal пуст;
- redaction текущей цели не может безопасно завершиться.

Quarantine всегда означает пустые labels и abstention по всем пяти осям.

## 9. Message-aware extraction rubric

При разборе OpenAI-compatible payload:

1. последний `role=user` является контейнером текущей цели;
2. `<context>...</context>` извлекается как retrieval context;
3. `<user_query>...</user_query>` имеет приоритет как current goal;
4. точный повтор query после закрывающего тега удаляется;
5. остальные части последнего user message считаются task wrapper;
6. более ранние user messages считаются history;
7. assistant/tool/system/developer messages хранятся раздельно;
8. redaction выполняется до любого persisted projection;
9. классификатор получает current goal, а не конкатенацию messages.

## 10. Adjudication

Для независимого challenge:

1. два annotator-а размечают строки независимо;
2. каждый label имеет evidence span;
3. расхождения по `create/update`, multi-label и abstention решает adjudicator;
4. сохраняются версия guide, annotator IDs, исходные labels, финальный gold и
   причина решения;
5. после freeze gold не меняется по результату model score.

Раскрытый sealed v1 остаётся историческим diagnostic и не используется для
изменения этого guide.
