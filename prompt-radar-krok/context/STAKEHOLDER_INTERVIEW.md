# Интервью со стейкхолдером — Татьяна Белякова

Дата: 2026-07-24

## Исходный контекст

После ограничения доступа к ChatGPT в РФ в компании создали внутреннюю
прослойку доступа к LLM. Сначала интерфейс работал через Telegram, затем был
заменён веб-интерфейсом на базе форка Open WebUI и внутренней интеграционной
прослойкой.

Внутренняя прослойка:

- маршрутизирует запросы между моделями;
- предоставляет сотрудникам единый интерфейс;
- аккумулирует пользовательские запросы и технические метрики.

После начала активного использования руководство поставило вопрос:

> Сколько денег продукт зарабатывает или экономит компании?

На продукт и команду тратится существенный годовой бюджет, поэтому простой
метрики количества пользователей и запросов недостаточно.

## Существующая методика для обычного LLM-чата

Для простых question-answer запросов компания использует экспертную оценку:

1. запросы классифицируются по тематикам;
2. для каждого класса экспертно задаётся ожидаемая экономия времени;
3. количество запросов умножается на оценку сэкономленных минут;
4. вводится коэффициент длины или сложности сессии:
   - короткая сессия — `0.3`;
   - средняя — `1`;
   - очень длинная — `2`;
5. итог переводится из минут в часы, рабочие дни и FTE.

Упрощённая текущая формула:

```text
saved_minutes =
    request_count
    × expert_minutes_for_category
    × session_coefficient
```

Это экспертная proxy-метрика, а не прямое измерение причинного эффекта.

## Новая проблема агентской платформы

Появился отдельный агентский продукт:

- обычным веб-интерфейсом пользуются примерно 1300 пользователей в месяц;
- агентской платформой — примерно 150 пользователей в месяц;
- при этом агентская платформа расходует примерно в пять раз больше токенов за
  месяц.

Поэтому количество пользователей, запросов и токенов по отдельности не
показывает эффективность. Агент может тратить больше токенов, потому что
выполняет длинную цепочку действий и заменяет значительный объём ручной работы.
Но высокий расход также может означать неэффективные циклы, ошибки, повторные
попытки или неудачный orchestration.

## Настоящий бизнес-вопрос

Нужно оценить не «сколько токенов потрачено», а:

1. какой законченный бизнес-процесс или его часть выполнил агент;
2. сколько человеческого времени стоило бы выполнение без агента;
3. был ли достигнут успешный результат;
4. сколько стоило выполнение агентом;
5. насколько результат надёжен и потребовал ли ручной доработки;
6. где дополнительные токены создают ценность, а где являются потерями.

## Рекомендуемая единица анализа

Для обычного чата единицей анализа может быть запрос или сессия.

Для агентского продукта единицей анализа должен стать `agent run` или
`completed job`:

```text
пользовательская цель
→ последовательность шагов и tool calls
→ результат
→ проверка успешности
→ человеческая доработка
→ стоимость и экономия
```

Один пользовательский запрос агенту может породить десятки LLM-вызовов.
Считать каждый внутренний вызов отдельной полезной задачей нельзя.

## Кандидат на экономическую модель

```text
gross_value =
    baseline_human_minutes
    × labor_cost_per_minute
    × success_probability
    × quality_coefficient

agent_cost =
    model_token_cost
    + infrastructure_cost
    + amortized_team_cost
    + human_review_minutes × labor_cost_per_minute

net_value = gross_value - agent_cost

ROI = net_value / agent_cost
```

Для времени:

```text
net_saved_minutes =
    baseline_human_minutes
    - user_active_minutes
    - human_review_minutes
    - rework_minutes
```

Все неизвестные параметры должны показываться как assumptions с диапазоном и
sensitivity analysis, а не как доказанные значения.

## Что необходимо измерять

- `run_id`, `user_id_hash`, `department`, `agent_id`;
- цель пользователя и классификация use case;
- start/end timestamp;
- число LLM-вызовов и tool calls;
- входные/выходные токены;
- стоимость моделей и инфраструктуры;
- результат выполнения;
- success/failure/partial success;
- ошибки и повторные попытки;
- время активного участия пользователя;
- время ручной проверки и доработки;
- пользовательская оценка;
- экспертный baseline ручного выполнения;
- confidence и источник baseline.

## Главный продуктовый вывод

Классификация и поиск сценариев остаются обязательными, но они становятся
частью более сильной системы:

> Prompt Radar должен находить use cases и показывать unit economics каждого
> сценария: где агент действительно экономит FTE и деньги, а где дорогие токены
> не превращаются в завершённую работу.

## Ограничения честности

- Нельзя напрямую сравнивать 1300 и 150 пользователей без нормализации по
  выполненным бизнес-задачам.
- Нельзя считать токены показателем пользы.
- Нельзя считать все запуски успешными.
- Нельзя выдавать экспертный baseline за фактически измеренную экономию.
- Для доказательства эффекта желательно провести time study, контрольную
  выборку или сравнение «с агентом / без агента».
- Денежные показатели должны иметь интервалы неопределённости.
